Geographic Clustering Sensitivity Analysis

The pure geographic DBSCAN clustering (see Geo Correlations) uses a 250km radius to decide what counts as "geographically co-located." A finding like "N geographic clusters" is only meaningful if it isn't just an artifact of that one radius choice. This re-runs the same clustering at 100km and 500km and compares each result against the 250km baseline using the Adjusted Rand Index (ARI) -- not just whether the cluster *counts* are similar, but whether the *same routers* actually end up grouped together. ARI near 1.0 means the clustering is robust to the exact radius; a low ARI means the reported figure is sensitive to that choice and should be reported with that caveat.

Going finer (100km) diverges substantially from the 250km grouping (low ARI) -- tighter radii split existing clusters into many smaller ones. Going coarser (500km) stays much more consistent with the baseline (higher ARI), which makes sense for density-based clustering: widening the radius tends to merge existing clusters rather than reshuffle which routers belong together. The practical takeaway: the exact cluster *count* is sensitive to the radius choice and shouldn't be over-interpreted as precise, but the coarser structure (which regions form dense hot-spots at all) is comparatively stable.

Other Statistical Safeguards In Use

  • Chi-square test of independence (Geo Correlations) -- confirms the country x version association is a real, statistically significant pattern (p < 0.05), not just visually different bars.
  • Wilson score confidence intervals (Geo Correlations country table) -- every per-country percentage is shown with its 95% CI, since several countries sit near the 5-router reporting minimum where a single router's difference can swing the percentage substantially.

Known, Disclosed Limitations

  • Third-party implementation identification (Java I2P vs. i2pd vs. I2P+) is not reliably possible from passive netDb data alone. The router.version field is a shared I2NP protocol version, not a per-implementation identifier -- confirmed directly: this project's own i2pd 2.60.0 and Java I2P 2.12.0 instances both report the identical "0.9.69". Only the two vantage-point routers this project directly controls can be tagged with certainty (see known_implementations.py); every other observed router's implementation is intentionally left unknown rather than guessed.
  • The system built here is broader than the proposal's originally-scoped "lean, static charts and report" deliverable -- it includes IsolationForest anomaly detection, PCA-based ASN reputation scoring, DBSCAN/K-means clustering, and a live interactive dashboard. This is disclosed here rather than implied as in-scope.
